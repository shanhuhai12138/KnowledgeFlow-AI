# 代码规范与评审流程

> 团队代码规范与 Code Review 流程说明，适用于所有成员提交代码前的自查与评审阶段的执行标准。

## 1. 命名规范

### 1.1 通用原则

- **含义清晰**：命名要能表达用途，禁止使用 `a1`、`tmp2`、`data` 之类的无意义名称。
- **统一风格**：全项目保持一致，不混用多种命名风格。

### 1.2 Java 后端

- 类名：大驼峰（PascalCase），如 `KnowledgeBaseController`。
- 方法名/变量名：小驼峰（camelCase），如 `createKnowledgeBase`、`documentCount`。
- 常量：全大写 + 下划线，如 `MAX_RETRY_COUNT`。
- 包名：全小写，如 `cn.iocoder.yudao.module.knowledge`。

### 1.3 前端（Vue/TypeScript）

- 组件文件：大驼峰，如 `ChatView.vue`、`DocumentList.vue`。
- 变量/函数：小驼峰；类型与接口：大驼峰。
- CSS 类名：短横线连接（kebab-case），如 `.kb-card-grid`。

### 1.4 数据库

- 表名：小写下划线，如 `kb_document`、`kb_query_log`。
- 字段名：小写下划线，如 `file_type`、`chunk_count`。
- 主键统一命名为 `id`，外键使用 `{目标表}_id` 格式。

## 2. 提交规范

### 2.1 Commit Message 格式

统一采用约定式提交（Conventional Commits）：

```
<type>(<scope>): <subject>

<body>
```

- `type`：`feat`（新功能）、`fix`（修复）、`refactor`（重构）、`docs`（文档）、`test`（测试）、`chore`（杂项）。
- `scope`：可选，模块名，如 `kb`、`document`、`chat`。
- `subject`：一句话描述，中文，不超过 50 字，结尾不加句号。

示例：`feat(document): 新增文档批量删除接口`

### 2.2 提交前自检

1. 本地运行测试：`mvn test` 或 `npm run test`，保证绿色。
2. 自查变更范围：只提交与本次任务相关的文件，禁止夹带无关修改。
3. 检查是否包含敏感信息：API Key、密码、内网地址一律不得入库。

## 3. 分支策略

- **主干开发**：`master` 为主干，所有开发基于主干拉取短期分支。
- 分支命名：`feature/{需求名}`、`fix/{问题名}`。
- 功能完成后合并回主干，合并前必须通过评审。

## 4. 代码评审流程

### 4.1 评审发起

1. 开发者在本地完成自测后，推送分支并创建合并请求（Merge Request）。
2. 在 MR 描述中说明：需求背景、改动范围、自测结果、需要评审重点关注的模块。
3. 指定至少 1 名评审人，复杂改动建议 2 名。

### 4.2 评审标准

评审人按下述清单逐项检查：

- **正确性**：逻辑是否正确，边界条件是否处理（空值、越界、并发）。
- **安全性**：是否存在注入风险、越权访问、敏感信息泄露。
- **性能**：是否有明显低效查询、N+1 问题、无谓的重复计算。
- **可维护性**：命名是否清晰，方法是否过长（建议不超过 80 行），是否缺少必要注释。
- **契约一致性**：API 字段命名是否符合 camelCase 契约，是否与前端类型定义一致。

### 4.3 评审结论

- **通过（Approved）**：评审人无阻塞性问题，可合并。
- **需修改（Changes Requested）**：存在阻塞性问题，开发者修改后重新提交评审。
- **意见（Comment）**：非阻塞建议，开发者可自行决定是否采纳。

### 4.4 合并与善后

1. 合并前确认 CI 流水线通过。
2. 合并采用 Squash 合并，保持主干历史整洁。
3. 合并后删除已合并的临时分支。
4. 线上发布后关注告警与日志，如出现异常立即回滚并排查。

## 5. 常见评审问题示例

- 接口未做参数校验，直接透传到数据库。
- 分页查询未加索引，数据量大时全表扫描。
- 异常被吞掉（catch 后不打印日志），导致线上问题无法定位。
- 前端硬编码后端地址，未走统一代理配置。
- 中文注释与代码混排不规范，影响阅读。

> 评审的本质是"帮团队把质量关"，不是找茬。发现问题第一时间给出可执行的改进建议，互相学习共同提升。

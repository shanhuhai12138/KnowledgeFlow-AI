# 微服务架构设计文档

> 本文档描述团队微服务化改造的总体架构设计，包括模块划分、服务通信、网关、配置中心与可观测性，供架构评审与新人学习使用。

## 1. 设计目标

- **高内聚低耦合**：按业务域拆分为独立服务，服务间不共享数据库表。
- **独立演进**：每个服务可独立开发、测试、部署与扩缩容。
- **故障隔离**：单个服务不可用不影响整体，通过熔断与降级保护链路。
- **可观测**：全链路日志、指标、链路追踪三件套齐备。

## 2. 模块划分原则

### 2.1 按业务域划分（DDD 思想）

- **用户与权限服务**：账号、角色、菜单、组织架构，是平台的基础服务。
- **知识库服务**：知识库 CRUD、成员管理、可见性控制。
- **文档服务**：文档上传、存储、元数据、版本历史。
- **检索服务**：语义检索、混合检索、重排序，对接向量数据库。
- **AI 编排服务**：文档解析分块、向量化、问答生成、Agent 工作流。
- **统计服务**：看板聚合、查询日志分析。

### 2.2 模块划分的边界判断

- 判断标准一：两个功能是否经常一起变更？一起变更频繁则应该在同一服务。
- 判断标准二：数据的一致性要求？强一致的数据应放在同一服务同一事务。
- 判断标准三：资源消耗是否差异巨大？例如 AI 计算密集任务应独立成服务。
- 反模式：按"技术层"拆分（如"接口服务""数据库服务"）是典型错误。

## 3. 服务通信

### 3.1 同步通信（REST）

- 服务间低频、实时的调用使用 REST/JSON。
- 统一响应体 `{ code, message, data }`，字段 camelCase。
- 必须设置超时（默认 3 秒），并处理超时与重试的幂等。

### 3.2 异步通信（消息队列）

- 高频、可容忍延迟的任务走消息队列：文档处理流水线使用 Redis Streams（`doc-pipeline`）。
- 好处：削峰填谷，生产者不关心消费者是否在线。
- 消费者必须幂等：同一条消息重复消费不产生副作用。

### 3.3 流式通信（SSE）

- AI 问答这类"逐步生成"的场景使用 SSE（Server-Sent Events）单向推送。
- 事件契约：`meta → content×n → sources → done`，前端按事件类型渲染打字机效果与引用卡片。

## 4. API 网关

- 统一入口，负责路由转发：`/admin-api/**` 转后端，`/ai/**` 转 AI 服务，`/` 转前端静态资源。
- 网关层职责：鉴权校验、限流、跨域处理、请求日志。
- 本项目开发环境由 Vite 代理承担网关职责，生产环境由 Nginx 承担。

## 5. 配置中心与密钥管理

- 配置分层：`基础配置（Docker Compose）→ 应用配置（application.yaml）→ 环境配置（.env）`。
- 密钥一律走环境变量：数据库密码、LLM API Key、MinIO 账号密码，禁止硬编码进代码仓库。
- `.env.example` 提供开发默认值，真实密钥放 `.env` 并加入 `.gitignore`。

## 6. 数据架构

- **MySQL**：业务数据（用户、知识库、文档元数据、查询日志），多租户通过 `tenant_id` 隔离。
- **Qdrant**：向量数据（文档分块后的 embedding），payload 带 `documentId/kbId/page`。
- **MinIO**：文档原始文件（PDF/DOCX/MD/TXT），S3 兼容协议。
- **Redis**：缓存 + Streams 消息队列。

## 7. 可观测性

- **日志**：统一 JSON 格式，包含 traceId，按天滚动。
- **指标**：Prometheus 采集 QPS、延迟、错误率、LLM Token 消耗。
- **链路追踪**：SkyWalking 或 OpenTelemetry，串联网关→后端→AI 服务全链路。
- **告警**：错误率超阈值、延迟 P99 超时、磁盘告警自动通知值班群。

## 8. 部署架构

```
用户 → Nginx → 前端静态资源（Vue3）
              ├─ /admin-api → 后端服务（Spring Boot :48080）
              └─ /ai → AI 编排服务（FastAPI :8000）
后端 ↔ MySQL / Redis / MinIO / Qdrant（Docker Compose 编排）
```

- 开发环境：`docker compose up -d` 一键启动全部基础设施。
- 生产环境：后端与 AI 服务容器化，通过 Nginx 反代，密钥走环境变量注入。

## 9. 演进路线

- 第一阶段：模块化单体（当前），按模块分包，接口契约冻结。
- 第二阶段：拆分独立服务，先拆 AI 编排与统计（资源消耗差异大）。
- 第三阶段：服务网格与全链路压测，沉淀平台化能力。

> 架构是演进而来的，不是一步到位的。当前"模块化单体 + 语言分工"（Java 业务 + Python AI）已满足答辩与演示需求，为后续拆分预留了清晰的边界。
